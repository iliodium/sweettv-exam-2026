# SWEET.TV: рекомендации пяти телепрограмм

Экзаменационный проект по рекомендательным системам. Из интервалов просмотра и телевизионного расписания построены положительные взаимодействия, затем на одном временном hold-out сравнены Content-based filtering, implicit ALS и Personalized PageRank (PPR), а также базовые методы и гибриды.

Репозиторий: https://github.com/iliodium/sweettv-exam-2026.

**Итоговый файл:** [`final_submission.csv`](final_submission.csv). Он содержит 1260 пользователей в порядке исходного шаблона и ровно пять различных положительных ID программ для каждого пользователя. Указанные ниже результаты относятся к этому конкретному файлу, без последующего переобучения на validation.

## Протокол данных

Использован исходный набор конкурса [sweet.tv — TV program recommender](https://www.kaggle.com/competitions/sweettv-tv-program-recommender). Данные скачиваются отдельно; исходные CSV, пользовательские истории, базы данных и выгрузки сессий не включены в публичный репозиторий.

- **TRAIN:** `[2020-03-09, 2020-06-29)` — 16 недель, недели 11–26.
- **Validation:** `[2020-06-29, 2020-07-27)` — 4 недели, недели 27–30.
- **Скрытый TEST:** `[2020-07-27, 2020-10-19)` — недели 31–42; доступно расписание, не поведение зрителей.
- Все модели, словари, IDF, профили и графы построены по TRAIN. Validation используется для выбора настроек; финальные модели также остаются замороженными и не дообучаются на validation.
- Просмотр сопоставляется с эфиром по телеканалу и пересечению интервалов. Перекрывающиеся фрагменты одного пользователя внутри одного эфира объединяются, чтобы не считать одну секунду дважды. Положительное взаимодействие — просмотр не менее **80% длительности конкретного эфира**.
- Для меток эфир должен полностью находиться внутри своего TRAIN/validation-периода. Для доступности кандидата используется начало эфира внутри целевого периода — одинаковое правило для validation и TEST. Это разные задачи: чистота обучающих меток и доступность программ.
- Матрица содержит число квалифицирующих эфиров пользователя для программы. Validation-цель — пять программ с наибольшей частотой таких эфиров; при равной частоте используется меньший ID.
- `tv_show_id = 0` — неопознанный эфир, не программа. Он не становится item. Его TRAIN-просмотры могут участвовать только в дополнительном профиле телеканалов.
- Повторные рекомендации уже просмотренных программ **разрешены для всех методов**: задача ориентирована на частоту просмотра телепрограмм, а не только на новые фильмы.
- Raw user ID хранятся строками: встречаются значения UInt64, превышающие предел signed int64. Модели используют отдельные позиционные индексы; исходные строки в submission сохранены.
- Кандидаты: 3957 программ validation-расписания и 6632 программ TEST-расписания. TEST-расписание задаёт только доступность и частоту эфиров; будущие просмотры не используются.

Фактически получено **461409** положительных TRAIN-эфиров / **169216** user–programme пар и **150304** положительных validation-эфиров / **80885** пар. В TRAIN наблюдаются 3405 программ; общий metadata-словарь содержит 9671 ID. В матрице 4789 пользователей — TRAIN-пользователи плюс известные пользователи шаблона. Из 1260 пользователей шаблона 13 не имеют положительной TRAIN-истории.

Общий fallback — TRAIN-популярность по числу различных положительных зрителей. Холодные пользователи получают одинаковый список доступных популярных программ независимо от модели. Если положительного сигнала недостаточно для пяти позиций, оставшиеся места также заполняются этим fallback без дубликатов. В ALS фактический пятый score у всех 1247 тёплых пользователей положителен: минимум 0.02849478 в обоих целевых периодах; правило `score > 0` не изменило его тёплый Top-5.

## Реализованные модели

- **Content-based:** TF-IDF по названию, категории, жанрам, людям и десятилетию; словарь и IDF обучаются только на метаданных программ с TRAIN-взаимодействиями. Профиль пользователя — взвешенная сумма item-векторов; ранжирование по косинусу. Будущие слова не меняют обученный словарь.
- **Implicit ALS:** официальная CPU-реализация `implicit`. Положительная уверенность `1 + alpha * log1p(count)`; незаполненные ячейки — implicit unobserved feedback, не низкие звёздные оценки. Выход — скалярное произведение факторов, без маски просмотренного. Настройки и seed записываются в результатах.
- **PPR:** TRAIN-граф совместных просмотров программ, коррекция степени пользователя и item cosine, не более 64 исходящих соседей, затем нормализация строк. Персональный restart задаётся TRAIN-историей. Масса dangling-узлов возвращается в тот же restart. Для каждого пользователя сохраняются residual, число итераций и факт сходимости; несошедшаяся конфигурация не используется как стационарный итог.
- **Дополнительные методы:** общая популярность, личная частота просмотров с вариантами временного затухания, channel-context и RRF. Их результаты показаны отдельно от обязательных методов.

Оценки этих моделей имеют разные шкалы и не являются взаимозаменяемыми вероятностями просмотра. PPR выдаёт массу случайного блуждания; ALS — некалиброванный dot product; content — косинус. Поэтому основной гибрид объединяет **ранги**, а не складывает сырые значения.

## Отрицательный результат: поправка на частоту эфиров

Дополнительно заранее зафиксирован небольшой grid для history и PPR: smoothing 4 TRAIN-псевдоэфира, множитель отношения target/TRAIN airing rate с ограничением `[0.25, 4]`, степень `{0, 0.5, 1}`. Использованы только известные расписания, без validation-обучения. Контроль `gamma=0` точно повторил исходные списки.

| База | gamma=0 | gamma=0.5 | gamma=1 |
|---|---:|---:|---:|
| History | 0.331182 | 0.327579 | 0.319998 |
| PPR | 0.337618 | 0.337532 | 0.327349 |

Все ненулевые варианты ухудшили validation MAP@5; поправка отклонена. Эти результаты не заменены предположением о том, что учёт расписания обязательно должен помочь.

## Воспроизведение

Проверенное окружение: **Python 3.12.14**, macOS arm64; `numpy 2.5.4`, `scipy 1.18.1`, `scikit-learn 1.9.1`, `implicit 0.7.3`, `duckdb 1.5.6`, `pandas 2.3.3`, `pyarrow 23.0.1`. Полная фиксация зависимостей — `requirements.txt`. Точные младшие цифры ALS и время выполнения могут зависеть от BLAS, платформы и числа потоков; в коде явно заданы seed и настройки потоков.

Из корня клона репозитория:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export PYTHONPATH="$PWD/src"
python -m unittest discover -s tests -p 'test_*.py' -v
```

**24 синтетических теста прошли**: 12 для метрик/формата и 12 для моделей. В частности, проверены AP@5 независимой рациональной арифметикой, исходные ID и формат пяти рекомендаций, граница train-only TF-IDF, воспроизводимость ALS, PPR против решения линейной системы, сохранение массы и честное сообщение о достижении лимита итераций. Это автоматические проверки, выполненные с AI-помощью, а не заявление о личном ручном пересчёте студента.

Получите архив конкурса со своего Kaggle-аккаунта после принятия правил. Ключи и cookies в репозиторий не помещаются. Следующие команды выполняются последовательно; замените путь к архиву своим:

```bash
python -m sweettv.profile_data --root "$PWD" --archive /absolute/path/sweettv-tv-program-recommender.zip
python -m sweettv.build_interactions --root "$PWD"
python -m sweettv.experiment --root "$PWD"
python -m sweettv.supply_extension --root "$PWD" --output "$PWD/artifacts/supply_extension"
python tools/audit_intervals.py --root "$PWD" --output "$PWD/evidence"
python tools/audit_experiments.py --root "$PWD" --output "$PWD/evidence"
```

`profile_data` распаковывает пять ожидаемых файлов, записывает их хеши и создаёт локальную DuckDB-базу. `build_interactions` строит события и metadata/candidate exports. `experiment` заново выполняет зафиксированный grid и сохраняет прогнозы, метрики и CSV по семействам. `supply_extension` читает замороженные score caches; без предыдущего шага она не запускается. Аудиты независимо проверяют интервалы, метки, MAP, когорту и соответствие CSV результатам.

Эти команды **не отправляют** результат в Kaggle и ничего не публикуют. Повторный запуск перезаписывает локальные производные результаты; исходный архив и распакованные CSV не редактируются. Построение DuckDB использует до 8–10 GB настроенного memory limit и восемь потоков; это конфигурация кода, а не измеренный пик памяти.

## Доказательства и ограничения

Публичная папка [`results/`](results/) содержит только отобранные агрегированные результаты и соответствие финального CSV score-артефакту. При воспроизведении подробные локальные доказательства появляются в `evidence/` и `artifacts/`: исходные хеши, учёт данных, конфигурации, per-user метрики, тесты и независимые аудиты. Эти локальные подробности и исходные пользовательские истории не предназначены для публичной публикации.

Независимый аудит сверил все 37 вариантов основного grid с точной рациональной арифметикой AP/MAP; максимальное расхождение MAP — около `5.6e-17`. Отдельный аудит реконструировал 33 выбранных user–airing случая из исходных CSV и проверил временные/диапазонные инварианты всех экспортированных событий. Выборочная проверка не доказывает полноту каждого исходного join.

Около 10.8% строк первого расписания имеют programme ID; неизвестные программы создают серьёзную границу наблюдаемости. Отсутствие записи в логе не доказывает, что пользователь никогда не смотрел передачу. Временной hold-out — один, выбор настроек на нём может переоценивать обобщение. Финальные модели намеренно не используют последние четыре недели для fitting, чтобы сохранить проверенный протокол. Offline MAP@5 и возвращённый Kaggle score не доказывают влияние на удовлетворённость, досмотры, retention или выручку. Онлайнэксперименты не проводились и не заявляются.

Проект подготовлен с AI-помощью в реализации, тестах, анализе и документации. В учебную систему исходные журналы передаются отдельно; в публичный репозиторий они не входят.
